Cold-start Speed Analysis

Making the first "Find my photos" search fast

Caching (Fix A) makes repeat searches instant — but the very first search over a fresh event folder still has to open and analyse every photo once. This page explains why that first pass is slow and the cheapest ways to cut its time, based on the real code in phorg/vision.py.

1 Why the first search takes time

On a cold cache, facefind() walks the photo list one photo at a time, on a single CPU core. For each photo it does the full pipeline:

flowchart LR A[Open photo file] --> B[Decode full-res JPEG
into memory] B --> C[Resize to ≤1600px] C --> D[YuNet: find faces] D --> E[SFace: fingerprint each face] E --> F[Compare to selfie] F --> A
Two lines in the code set the cold-start cost:
• img = cv2.imread(path) — decodes the entire full-resolution photo.
• the for p in native_paths: loop runs sequentially — only one core is used, no matter how many the PC has.

Takeaway: most of the first-pass time is decoding full-size photos and running the detector — and all of it on a single core. Those are exactly the three cheap levers below.

3 Cheap ways to make the first pass faster

All free code changes, ordered by impact-for-effort. They stack — doing all three can cut a cold search to a fraction of today's time.

1 · Use all CPU cores (parallel embedding) BIGGEST WIN · $0

The photo loop is single-threaded today. OpenCV releases Python's lock while it decodes and runs the models, so a small thread pool can process several photos at the same time. On a 4-core PC this is roughly a 3–4× speed-up for free.

Keep the pool size ≈ number of cores, and reuse one model set (see the low-RAM doc, Fix B) so memory stays flat. Pair it with a bounded queue so 20 guests don't each spawn their own pool.

2 · Decode photos at reduced resolution $0

Right now the full photo is decoded, then shrunk to 1600 px and thrown away — wasted work. OpenCV can decode a JPEG at half or quarter size directly using cv2.IMREAD_REDUCED_COLOR_2 / _4. Faces are still easily detected at that size, but decoding is far cheaper and uses much less memory.

Bonus: this also lowers the peak memory per photo — directly helping the low-RAM scenario, not just speed.

3 · Detect on a smaller image $0

The detector cost grows with image size. Feeding YuNet an image capped at ~800–1024 px (instead of 1600) speeds detection with little effect on match quality for normal event photos, where faces are a decent size.

4 · Show results as they arrive (feels instant) $0

The job already reports progress(done, total, matches). Streaming each match to the guest the moment it's found — instead of waiting for the whole folder — makes the search feel fast even before it fully finishes. Perceived speed matters as much as raw speed.

4 The trick that hides the wait entirely

Pre-warm the cache when the host starts sharing $0

The first search is only slow because the cache is empty. So don't wait for a guest — the moment the host enables the share (api_share_enable), kick off a background pass that embeds every photo into the Fix A cache.

  • Guests usually arrive minutes later — by then the folder is already analysed.
  • The first guest's search is then as instant as everyone else's.
  • It reuses the exact same cache and code path as Fix A — no new machinery.
flowchart LR H[Host enables share] --> W[Background pre-warm:
embed all photos once] W --> Z[(faces.db cache)] G[Guest searches later] --> Z Z --> R[Instant match]
Net effect: parallel + reduced-resolution decode make the one-time pass fast, and pre-warming moves that pass to before anyone is waiting — so the first "Find my photos" feels instant.
