Performance & Scaling Analysis

Face ID under load: 20 guests at once on a low-RAM PC

A plain-English look at what happens inside the FaceFind feature when a crowd searches for their photos at the same time, why a machine with little RAM struggles — and the cheapest ways to make it scale smoothly. Based on the actual code in phorg/vision.py and phorg/server.py.

1 How the feature works today

The whole thing runs locally on one PC — no cloud, no GPU. Face matching uses two small AI models loaded by OpenCV on the CPU:

🔍 YuNet — the "find a face" model

Scans a photo and returns boxes around every face it sees.

🧬 SFace — the "face fingerprint" model

Turns each face into a list of ~128 numbers (an embedding). Two faces match when their number lists point the same way (cosine similarity ≥ the threshold).

When a guest opens the link and submits a selfie, the server runs one background job for that guest. Look at what the job actually does (from vision.facefind()):

  • Loads a fresh copy of both models — emb = FaceEmbedder() is called inside every job.
  • Fingerprints the selfie once → one reference vector.
  • Re-opens and re-scans EVERY photo in the event folder — decodes the image, runs YuNet to find all faces, runs SFace on each face, then compares to the selfie.
The key detail: the heavy work (decoding photos + running the two models on every face) is redone from scratch for each guest. Nothing is cached and shared between guests. This is the root of every problem on this page.

2 What happens when ~20 people search at once

The built-in web server (ThreadingHTTPServer) starts a new thread per request, and each FaceFind job spawns another background thread. There is no limit on how many run at the same time.

So 20 guests pressing "Find my photos" together means 20 identical heavy jobs running in parallel, each one independently chewing through the entire photo folder.

The multiplication problem. If the event has 1,000 photos, the work isn't 1,000 face-scans — it's 20 × 1,000 = 20,000 face-scans, because every guest re-scans all 1,000 photos. The same photo gets decoded and analysed 20 times over.

3 Why a low-RAM machine struggles

Two things eat memory at the same moment, multiplied by 20:

What sits in RAMRoughly per job× 20 guests
The two AI models loaded by OpenCVtens of MBhundreds of MB (duplicated)
The photo being decoded right now (a 12 MP JPEG expands to a big raw bitmap in memory) ~30–50 MB per open image0.6–1 GB just for in-flight images
Face crops + embedding math buffers (NumPy)a few MBtens of MB

When those add up past the free RAM, the operating system doesn't politely stop — it does one of these, all bad:

💽 Swapping (page thrashing)

Windows starts using the disk as fake RAM. Disk is thousands of times slower, so every job crawls. A search that took seconds now takes many minutes; the whole PC feels frozen.

💥 Out-of-memory errors

A photo decode or model load can fail with a MemoryError. That job dies and the guest sees "something went wrong" — even though other guests may succeed.

🧮 CPU starvation

20 CPU-bound threads on, say, 4 cores means each guest gets ~1/5 of a core. Everyone's search slows to a near-standstill and the server barely answers other clicks.

🪦 Process killed / unresponsive

In the worst case Windows terminates the app, or it stops responding to new guests entirely until jobs finish.

In one sentence: the app won't corrupt anything or lose photos (it only reads them), but with low RAM and 20 simultaneous searches it will get painfully slow, some searches will fail, and the PC may become unresponsive until the queue drains.

4 The tell-tale symptoms

  • Progress bars stall for everyone at the same time.
  • Fans spin up, disk light stays solid (that's swapping).
  • Some guests get an error while others slowly succeed.
  • The first few guests are fast, later ones are glacial as RAM fills.
  • The host UI (scan / organise buttons) lags because the server threads are saturated.

5 How to fix it — cheaply

Good news: you don't need a bigger server or a GPU. The biggest wins are free code changes that remove the wasted, repeated work. They're ordered by impact-for-effort.

A · Compute each photo's face fingerprints once, then reuse them BIGGEST WIN · $0

Right now every guest re-embeds every photo. Instead, scan the event folder one time (when sharing starts, or the first time anyone searches) and store the embeddings. After that, a guest's search is just comparing their selfie's numbers to the saved numbers — math on a list, no image decoding, almost no memory.

The project already has the tool for this: hashcache.MetaCache caches per-photo data by path + size + modified-time (it's used for duplicate detection). The same pattern can store face embeddings so re-scans are near-instant.

B · Load the AI models once and share them $0

Create one FaceEmbedder when sharing turns on and reuse it, instead of building a new one inside every job. That instantly removes the ×20 duplicate models from RAM.

C · Limit how many searches run at once (a small queue) $0

Add a worker pool of, say, 2–4 jobs (a Semaphore or a small thread-pool). Guest #5 onward simply waits in line for a few seconds instead of everyone crashing together. Total throughput actually goes up because the CPU and RAM aren't thrashing.

Rule of thumb: allow about one worker per CPU core, capped so total memory stays within free RAM. On a small PC that's often just 2–3.

D · Compare all faces in one matrix operation $0

Once embeddings are cached, stack them into a single array and do one NumPy multiply to score every photo against a selfie at once. This is far faster and lighter than the current per-photo Python loop.

E · Shrink images before detecting $0

The code already caps images at 1600 px. Dropping the detection size to ~1024 px (and freeing each image right after use) cuts the peak memory per job with almost no loss in match quality for event photos.

Only if you outgrow one PC — modest paid options

🖥️ One cheap cloud VM

A small always-on Linux box (a few dollars a month) that holds the cached embeddings and answers guests. Handles far more people than a laptop on Wi-Fi.

⚡ Optional GPU / ONNX Runtime

Only worth it for very large events (10k+ photos). The models already exist as ONNX, so switching to a GPU runtime is a small change — but it's the most expensive step and usually not needed if caching (Fix A) is done.

Reach for paid hardware last. Caching + a small queue removes ~95% of the load for free; most events never need more.
