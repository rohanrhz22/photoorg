FaceFind (Face ID) — how it works, end to end

A privacy-first face-matching feature: point it at an event folder, a guest submits a selfie, and every photo they appear in — including group shots — is found locally on the host PC and offered as a download. Nothing is uploaded to any cloud for the matching itself.

1 What it is

Two personas share one local web app served by Python's standard-library HTTP server.

👤 Host (event owner)

Runs phorg on their PC, picks the event folder, and turns on a guest portal. Optionally exposes it to the internet via a Cloudflare quick tunnel.

🙋 Guest

Opens a link (with a secret token), submits a selfie from a phone camera or file, and downloads the photos they appear in — one by one or as a ZIP.

Privacy stance: face detection & recognition run entirely on the host machine using on-device ONNX models. The guest's selfie is used transiently for matching and the event photos never leave the host except as direct downloads the guest requests.

Host setupConnect folder → FaceFind tab → /api/share/enable. A 10-char token is minted; LAN URLs (and, if online, the HTTPS tunnel URL) are returned with a QR.
2
Guest opens linkThe SPA sees ?g=token, switches to guest mode, calls /api/share/status to confirm the link is live and shows the event name.
3
Selfie captureFile picker or native camera (works over HTTPS). The image is sent as a data-URL to /api/facefind/selfie and stored transiently in %TEMP%/phorg_facefind.
4
Match job/api/share/find/start records the guest and launches a background thread: the selfie becomes a reference embedding; every event photo is scanned.
5
Progress + resultsThe portal polls /api/cluster/progress for done/total, then renders matches (sorted by score) with thumbnails from /api/thumb.
6
DownloadPer-photo /api/download streams the original; “Download all” builds a ZIP in memory via /api/download/zip. Originals never move.

5 The matching pipeline (the actual "Face ID")

How a selfie becomes a set of matches. Similarity is cosine distance between L2-normalised 128-D SFace embeddings.

flowchart TB
  A["Selfie image"] --> B["Decode (OpenCV, Pillow fallback)"]
  B --> C["Downscale to max 1600px"]
  C --> D["YuNet: detect faces"]
  D --> E{"Face found?"}
  E -- no --> X["Error: no_face_in_selfie"]
  E -- yes --> F["Pick largest face → alignCrop → SFace feature
= reference vector (unit-norm)"]

  subgraph SCAN["For every event photo"]
    G["Decode + downscale"] --> H["YuNet: detect ALL faces (max 12)"]
    H --> I["SFace embed each face (unit-norm)"]
    I --> J["cosine = dot(face, reference)"]
    J --> K["keep best score for the photo"]
  end

  F --> SCAN
  K --> L{"best ≥ threshold
(default 0.40)?"}
  L -- yes --> M["Add to matches with score"]
  L -- no --> N["Skip"]
  M --> O["Sort matches by score desc → return"]

Why "all faces"?

Group photos: the guest may be a tiny face in the back. embed_all() embeds up to 12 faces per image so small faces still match.

Threshold

Guest "Match strictness" slider maps to the cosine threshold (default 0.40). Higher = stricter, fewer false positives.

Cost

O(images × faces) embeddings per guest. No caching today — each guest re-embeds the whole folder.

6 Security model

🔒 Local-first default

Bound on all interfaces so LAN phones can reach it, but non-local requests are refused unless sharing is explicitly on.

🎫 Token-gated

Every link carries a per-session token (?g=…). The guest whitelist, thumbnails, single-file downloads and the zip all validate it.

🚧 Route whitelist

Guests can only hit share/status, facefind/selfie, share/find/start, cluster/progress|cancel, thumbs & downloads. Scan/plan/apply/undo stay host-only.

📁 Match confinement

_guest_may_fetch() lets a guest read only the photos their own search matched — not arbitrary files under the event folder — so sequential filenames can't be enumerated.

🛡️ DNS-rebind guard

Host-header checks accept only localhost, private IPs, or the app's own tunnel hostname.

🌐 HTTPS when online

The Cloudflare tunnel terminates TLS, so guest traffic is encrypted end-to-end and phone cameras are unlocked.

8 What to improve — and which services would help

Grouped by goal. Choices preserve the local-first stance unless noted cloud.

🎯 Better accuracy
Swap SFace for a modern ArcFace/InsightFace model (e.g. buffalo_l) run via ONNX Runtime, or use DeepFace. Add face-quality gating (pose, blur, size) before embedding. Optionally ensemble two models.
InsightFaceONNX RuntimeDeepFace
⚡ Speed & scale
Index once, reuse forever: pre-compute every photo's face embeddings when the folder is shared, store them in a vector database, and answer each guest with an approximate-nearest-neighbour (ANN) query instead of a full re-scan. This turns per-guest cost from O(all photos) into O(1) lookup.
FAISSQdrantMilvuspgvector
🖥️ Hardware accel
Use onnxruntime-gpu / CUDA or DirectML for detection + embedding; batch images through the model.
CUDAonnxruntime-gpuDirectML
🧵 Concurrency
Replace ad-hoc threads with a real job queue so many guests can be served fairly with retries and back-pressure.
Redis + RQCelery
⬇️ Downloads
Stream the ZIP in chunks (remove the RAM ceiling & timeout risk), or offload delivery to object storage with short-lived presigned URLs served over a CDN — guests download straight from the edge.

Highest impact, lowest effort

Chunked ZIP streaming + an embedding cache/index. Together they remove the two biggest pain points (RAM-bound downloads and per-guest full re-scan).

11 Capacity & cost per phase — how many customers each tier serves

"Customers" here = concurrent guests searching/downloading, and the number of events (host folders) you can run. Numbers are realistic planning figures, not hard limits.

Phase 0 · Today (laptop + quick tunnel)

Cost: $01 event at a time

CPU-bound, in-RAM zip, per-guest full re-scan. Comfortable for ~5–10 concurrent guests and a few hundred to ~2–3k photos. Beyond that, matching queues up and big zips risk the ~100 s tunnel window.

Phase 1 · Quick wins (still on the host PC)

Cost: $01 event

Chunked-zip streaming + an embedding cache remove the two worst bottlenecks. Same machine now handles ~20–30 concurrent guests and 10k+ photos, because each photo is embedded once, not per guest.

Phase 2 · Scale (small VPS + vector index)

≈ $10–30 /momany events

FAISS/Qdrant ANN turns each search into a millisecond lookup. A single 4-vCPU box serves ~50–100 concurrent guests and comfortably 1,000–3,000 guests / month across multiple events. Photos on R2 → downloads no longer touch your server.

Phase 3 · Accuracy / burst (add GPU on demand)

≈ $50–300 /molarge events

GPU only when indexing big folders (spin up spot GPU, index, spin down). Handles 50k–100k photos per event and indexing bursts; steady-state serving stays on the cheap CPU box. Good for 5,000–15,000 guests / month.

Phase 4 · SaaS (multi-tenant, autoscale)

scales with usageunlimited events

Stateless API behind a load balancer + queue workers + object storage. Capacity becomes "how many workers you run". Tens of thousands of guests / month; cost tracks storage + worker hours, with R2 keeping bandwidth ~free.

Managed-API variant cloud

≈ $1 / 1,000 imgs

If you use Rekognition/Azure/Google instead of self-hosted models, capacity is "unlimited" but cost is per-image. A 10k-photo event ≈ $10 to index; 100 events/mo ≈ $1,000. Trades privacy + money for zero model ops.

12 Making it fully online — at the lowest running cost

Goal: no host PC required, works for anyone on the internet, and costs a few dollars a month at small scale. The trick is zero-egress storage for photo delivery and a single small always-on box for the API.

1 · Frontend on free static hosting

Ship the SPA to Cloudflare Pages / Netlify / Vercel (free). No server cost for the UI.

2 · One small always-on API box

A Hetzner CX22 (~$4/mo) or Fly.io instance runs the FastAPI backend, a Redis queue, and CPU ONNX-Runtime workers. No GPU needed at small scale.

3 · Photos on Cloudflare R2

Upload once. Guests download directly from R2 via short-lived presigned URLs — $0 egress means downloads don't cost you bandwidth or hit your server.

4 · Index once, search fast

On upload, compute embeddings and store them in Qdrant (self-hosted on the same box). Each guest search is a millisecond ANN query, not a re-scan.

5 · Prebuild album zips

Generate a guest's zip in a worker and drop it in R2; hand back a presigned link. Removes the in-RAM zip limit and any tunnel timeout.

6 · Auth & abuse control

Signed, expiring links; per-event rate limits; optional Cloudflare Access (free ≤ 50 users) or a PIN in front of the portal.

Why it's cheap: the two things that normally blow up a photo app — egress bandwidth and GPU — are avoided. R2 has no egress fees, and CPU ONNX Runtime + a vector index is fast enough because each photo is embedded only once.
When costs rise: heavy indexing bursts (add spot GPU by the hour), >10k concurrent guests (add worker boxes behind a load balancer), or switching to a managed face API (per-image pricing). Scale these only when volume justifies it.
